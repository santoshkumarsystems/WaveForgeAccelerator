# WaveForge Accelerator Architecture

WaveForge Accelerator is an experimental **end-to-end AI accelerator compiler/runtime project**.

It begins with **AI model training — a neural network trained from scratch in PyTorch** on deterministic physical-wave data generated by cuWaves, then carries that trained model through ONNX, real inference runtimes, Apache TVM compiler integration, SRAM-aware execution planning, and a C++ accelerator-style runtime.

> **Engineering principle:** Correctness before optimization. Visibility before abstraction. Hardware constraints before compiler automation.

## 2. AI model training layer

WaveForge Accelerator does **not** begin with a downloaded pretrained model.

The project builds the AI model pipeline itself:

```text
cuWaves physics
   ↓
deterministic dataset generation
   ↓
10,000 examples
   ↓
64 spatial samples per example
   ↓
PyTorch WaveRegressor
   ↓
neural network training from scratch
   ↓
learned amplitude + wavelength mapping
```

The physical source is a 1D spatial wave:

$$
F(x,t) = A \sin(kx - \omega t + \phi)
$$

$$
k = \frac{2\pi}{\lambda}
$$

The current dataset uses a spatial snapshot at fixed time. The model predicts:

```text
amplitude
wavelength
```

Wavelength is directly encoded in the spatial oscillation. Temporal frequency is not uniquely identifiable from a single fixed-time spatial snapshot without additional temporal information or another physical constraint.

### Current neural network

```text
64 inputs
  ↓
Linear 64 → 32
  ↓
ReLU
  ↓
Linear 32 → 16
  ↓
ReLU
  ↓
Linear 16 → 2
  ↓
denormalization
```

The trained network contains:

```text
2,642 learned FP32 parameters
```

The exported ONNX graph also contains four FP32 normalization constants.

Validated training configuration:

```text
seed:       7
train/val:  8000 / 2000
batch:      128
optimizer:  Adam
lr:         1e-3
epochs:     200
```

Recorded validation MAE:

```text
amplitude:  0.005691
wavelength: 0.005026
```

## 4. Apache TVM compiler layer

WaveForge Accelerator uses Apache TVM for the compiler-side path.

Validated compiler flow:

```text
ONNX
  ↓
Relax
  ↓
PrimFunc / TIR analysis
  ↓
WaveForge target contract
  ↓
SRAM-aware scheduling policy
  ↓
BYOC partitioning
  ↓
BYOC → ExecutionPlan bridge
  ↓
integrated compiler plan
```

### BYOC partitions

The current graph partitions into five WaveForge external-codegen regions using the internal backend name `waveaccel`:

```text
waveaccel.matmul_bias_relu × 2
waveaccel.matmul_bias      × 1
waveaccel.multiply         × 1
waveaccel.add              × 1
```

Exact validated mapping:

```text
P0 waveaccel.matmul_bias_relu → plan nodes [0, 1]
P1 waveaccel.matmul_bias_relu → plan nodes [2, 3]
P2 waveaccel.matmul_bias      → plan node  [4]
P3 waveaccel.multiply         → plan node  [5]
P4 waveaccel.add              → plan node  [6]
```

The current model has full WaveForge BYOC graph coverage.

### Compiler scope

Implemented:

```text
ONNX → Relax
Relax / PrimFunc / TIR inspection
target-contract modeling
SRAM-aware scheduling
TVM BYOC pattern matching / partitioning
BYOC → WaveForge ExecutionPlan integration
integrated BYOC + SRAM-aware compiler-plan emission
```

Not yet implemented:

```text
TVM RunCodegen backend
native TVM TargetKind
custom TVM runtime Module
proprietary machine-code generation
LLVM / MLIR backend integration
```

These are future compiler-depth milestones and are not claimed by the current implementation.

## 5. Compiler/runtime target contract

The compiler-side target contract is the source of truth for the accelerator model.

Current contract:

```text
target:              waveaccel-sim
schema:              1
dtype:               float32
element size:        4 bytes
supported ops:       Gemm, Relu, Mul, Add
memory hierarchy:    device_memory → sram
GEMM tiling axis:    output_channel
tile unit:           complete_output_weight_row
tiled fixed init:    bias
```

The same contract semantics are transported into C++.

The runtime rejects incompatible:

```text
dtype
logical memory-space assumptions
supported-op contracts
SRAM / staging-capacity contracts
```

## 6. Compiler/runtime boundary

The compiler owns:

```text
target capabilities
operator support
dtype constraints
SRAM / transient constraints
GEMM staging policy
GEMM tiling policy
BYOC partition selection
node / tile execution-plan decisions
```

The runtime owns:

```text
execution-plan validation
task scheduling
deterministic logical model addressing
DeviceCommand lowering
cold/warm residency state
device / SRAM bounds enforcement
command execution
real numerical execution
profiling
```

This separation lets the compiler make hardware-aware decisions while the runtime remains responsible for safe execution.

## 8. SRAM-aware execution

### 16 KiB configuration

The model working set fits.

```text
model initializer bytes: 10584
transient reservation:     392
working set:              10976
```

Behavior:

```text
cold inference:
  stage model into SRAM

warm inference:
  keep model resident in SRAM
```

For the validated warm path:

```text
Host → Device bytes: 264
Device → SRAM bytes:   0
```

### 4 KiB configuration

The model does not fit.

```text
SRAM capacity:                4096 B
Transient reservation:        392 B
Initializer staging capacity: 3704 B
```

For the first GEMM:

```text
weight bytes: 8192
bias bytes:    128
row bytes:     256
```

After reserving the bias:

```text
available weight bytes = 3576
floor(3576 / 256) = 13 output rows
```

The compiler therefore emits:

```text
13 + 13 + 6 output-channel tiles
```

Exact validated first-GEMM staging layout:

```text
bias:
  SRAM offset 0
  128 B

weight tile area:
  begins at SRAM offset 128

tile 0:
  logical device offset 0
  3328 B
  outputs 0..12

tile 1:
  logical device offset 3328
  3328 B
  outputs 13..25

tile 2:
  logical device offset 6656
  1536 B
  outputs 26..31
```

Later GEMMs fit whole in the staging region:

```text
Gemm1: 2112 B
Gemm2:  136 B
Mul:      8 B
Add:      8 B
```

For the validated 4 KiB path:

```text
Host → Device bytes: 264
Device → SRAM bytes: 10584
```

This is real row-aligned output-channel decomposition under a simulated SRAM capacity. It is not a full tensor-core-style M/N/K tiling system.

## 9. ExecutionPlan and CompiledRuntimeSchedule

The compiler emits an execution plan describing graph order, initializer requirements, and SRAM decisions.

```text
TVM / target policy
        ↓
ExecutionPlan
        ↓
CompiledRuntimeSchedule
        ↓
DeviceCommandStream
```

The manual scheduler was implemented and validated first.

The compiler-generated schedule was then required to match that known-correct manual schedule for the current model/target.

This is the project methodology in practice:

```text
correctness before optimization
visibility before abstraction
hardware constraints before compiler automation
```

## 11. MockDevice contract

`MockDevice` is the generic accelerator-style backend used by WaveForge Accelerator.

It validates:

```text
device source range
initializer staging range
full SRAM capacity
staging-capacity contract
target-contract compatibility
```

Invalid accesses are rejected before execution.

Validated logical device bytes:

```text
10,584
```

Validated 4 KiB SRAM configuration:

```text
SRAM bytes:                4096
initializer staging bytes: 3704
```

`MockDevice` models generic accelerator behavior only. It does not claim to reproduce proprietary hardware.

## 12. Cold/warm residency

WaveForge Accelerator models model residency explicitly.

### 16 KiB

```text
cold:
  model is staged

warm:
  model remains SRAM-resident
```

### 4 KiB

```text
model cannot remain wholly resident
weights are staged / tiled per inference
```

This makes memory pressure and residency behavior visible without pretending to model a proprietary memory subsystem.
